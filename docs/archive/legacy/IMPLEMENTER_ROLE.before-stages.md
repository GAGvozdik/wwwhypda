2. **ТАБЛИЦЫ:** Для таблиц используйте только **ag-grid-community**.
3. **СТИЛИЗАЦИЯ (SCSS):**

   - Весь текст должен использовать шрифт **Afacad_Flux**.
   - **РАЗМЕРЫ ШРИФТОВ** задаются **ТОЛЬКО** через CSS-переменные (например, `--main-font-size`), определенные в `wwwhypda-frontendV2/src/components/menu.module.scss`.

## Адаптированные правила frontend для wwwhypda

### Область действия и пути

Правила ниже дополняют предыдущие требования для любых frontend-задач из `TASKS.md`. Общие принципы адаптированы из `nb/neurobaza/docs/plan/contracts/front-real-rules.md`, `frontend-boundaries.md` и связанных планов сохранения UX; реализация neurobaza не является спецификацией wwwhypda.

- Файлы ролей и `TASKS.md` находятся в рабочем каталоге `32_wwwhypda`; корень приложения — `wwwhypda/` внутри него. Все ранее перечисленные пути фронтенда, бэкенда, Docker и Nginx отсчитываются от этого корня приложения.
- Не переносить маршруты, палитру, шрифт MyRuda, FastAPI, landing/app-разделение, APP_BASE_PATH, billing, API-ключи, чат, Markdown/SSE-stack и структуру neurobaza. Не устанавливать зависимости только по их упоминанию в исходных правилах.
- Рабочий процесс остаётся двухчатным через `TASKS.md`; stage/reviewer/approval/archive workflow neurobaza не вводится.
- Не читать перечисленные ранее env-файлы, корневые `.env`, `.env.development`, другие env-файлы и файлы секретов. Имена переменных изучать по исходникам и документации. Разрешённые команды Docker могут использовать env-файлы без вывода их содержимого; не запускать команды раскрытия окружения вроде `docker compose config` или `printenv`.

### 1. Компоненты, библиотеки и типы

- Использовать существующие React + TypeScript + Vite, SCSS Modules, Axios, Redux и MUI. Для новых стандартных элементов преимущественно использовать уже подключённые MUI-компоненты. Не добавлять альтернативную UI-библиотеку и не переписывать рабочие нестандартные элементы ради унификации.
- Компоненты должны иметь понятную ответственность и обычно быть короче 400–600 строк. Не раздувать их; при необходимости выделять связанные компоненты, hooks и helpers в пределах задачи, сохраняя поведение, комментарии и закомментированный код.
- Переиспользовать общие типы из `wwwhypda-frontendV2/src/common/types.ts`. Не создавать дублирующие типы без проверки существующих.
- Сохранять структуру `src/redux/store.ts` и `src/redux/actions.ts`, существующие actions и способ работы с общим состоянием. Не вводить второй store и не мигрировать Redux вне задачи.

### 2. API и защита маршрутов

- Все HTTP-запросы к Flask выполнять через существующий Axios-instance из `wwwhypda-frontendV2/src/components/api.tsx`. Вызовы из компонентов через импортированный instance допустимы. Не создавать второй instance, прямой fetch или отдельный транспорт в обход этого файла без явного требования.
- Instance использует `VITE_API_BASE_URL`; не подменять его `VITE_BASE_URL`/`APP_BASE_PATH` из neurobaza. Новые endpoints и payload должны соответствовать реальному Flask API wwwhypda.
- Auth/session реализованы в `src/components/users/`: перед изменением изучить `useAuthCheck.tsx`, `tokenRefresh.ts`, `auth/`, `routes/` и только необходимые backend endpoints. Не создавать параллельную авторизацию и не считать refresh/interceptor-поведение neurobaza уже реализованным здесь.
- Сохранять существующий cookie/CSRF flow, `withCredentials`, CAPTCHA, redirects и guards. Не отключать защиту для устранения UI-ошибки; JavaScript не может удалить HttpOnly cookies.
- Frontend-validation улучшает UX, но не заменяет backend-validation. Права на просмотр, редактирование и административные действия определяются сервером; скрытые элементы и React guards не обеспечивают защиту API.
- Не выводить в консоль токены, cookies, пароли, секреты, полные auth/network error objects или чувствительные тела запросов/ответов. Пользователю показывать безопасное сообщение из общего словаря.

### 3. Только AG Grid Community

- Таблицы реализовывать только на бесплатных возможностях `ag-grid-community`; `ag-grid-react` разрешён как React-обёртка.
- Запрещены `ag-grid-enterprise`, Enterprise-модули, их регистрация, платные функции/API и другая табличная библиотека, включая MUI Data Grid. Старые зависимости не дают разрешения использовать их.
- Если требование нельзя выполнить бесплатным API, описать ограничение и предложить Community-совместимое решение; платную функциональность самостоятельно не подключать.
- Сохранять предусмотренные задачей данные, редактирование, сортировку, фильтрацию, экспорт и пагинацию. Не переносить серверную пагинацию, внешний MUI pager, page size 10, fixed-height foundation или мобильные списки neurobaza как обязательные для wwwhypda.
- Известное расхождение: в `package.json` есть `ag-grid-enterprise` и нет прямого `ag-grid-community`, хотя исходники импортируют Community API. Не использовать Enterprise в новых изменениях. Удаление старой зависимости, явное подключение совместимых Community/React-пакетов и проверку имеющихся возможностей выполнить по отдельной задаче в `TASKS.md`; не удалять комментарии с Enterprise-импортами и не менять зависимости попутно.

### 4. Палитра, шрифт, темы и SCSS

- Единственный источник цветов и размеров шрифтов — `wwwhypda-frontendV2/src/components/menu.module.scss`. Примеры реальных переменных: `color: var(--tree-text)`, `background-color: var(--body-color)`, `font-size: var(--main-font-size)`.
- Цветовые переменные wwwhypda содержат готовые CSS-цвета, а не RGB-каналы neurobaza. Не копировать конструкции `rgba(var(--accent-primary), 1)` или чужие имена переменных без соответствующих определений.
- Все цвета использовать через `var()`, размеры шрифтов — только через переменные общей палитры. Недостающую переменную добавить в общий файл с корректными значениями для обеих тем, если это требуется задачей; не хардкодить цвет или размер шрифта локально.
- Весь интерфейс использует `Afacad_Flux`, включая MUI, таблицы, input, tooltip и dialog. Не заменять его на MyRuda или шрифт библиотеки по умолчанию.
- Сохранять механизм Redux `isDarkTheme`, localStorage `isDarkTheme` и CSS Modules `.dark`. Не внедрять `ThemeProvider`, `createTheme`, `CssVarsProvider`, `useColorScheme` или другую параллельную систему тем без явного требования.
- Основные стили размещать в SCSS-модуле рядом с компонентом. Если библиотечная стилизация MUI не решается SCSS, разрешены необходимые `sx`/`slotProps` и существующие библиотечные механизмы в TSX. Это уточнение правила SCSS, а не перенос всех стилей в TSX; цвета и размеры шрифтов также брать через `var()`.
- Для portal-компонентов MUI (tooltip, popper, menu, dialog) проверять доступность переменных текущей темы и стиль тела/хвостика. Использовать действующий theme scope/контейнер; не отключать portal механически, если это ломает позиционирование или доступность.

### 5. Тексты интерфейса

- Короткие пользовательские строки — подписи кнопок и полей, заголовки, tooltip, сообщения ошибок/успеха — хранить в `wwwhypda-frontendV2/src/common/error_messages.json`, проверяя и переиспользуя существующие ключи.
- Сохранять язык текущего интерфейса: в wwwhypda сообщения преимущественно английские. Русский язык ответов и документации не означает перевод UI на русский.
- В фактически редактируемом компоненте переносить короткие литералы интерфейса из JSX/return в общий словарь. Не выполнять массовую миграцию соседних компонентов вне задачи.
- Большие юридические документы, пользовательские данные, API identifiers и технические строки не являются короткими UI-текстами и не переносятся в этот словарь по данному правилу.

### 6. UX, доступность и поддерживаемые размеры

- Перед изменением общего компонента, SCSS, темы или таблицы определить все страницы-потребители и проверить их после изменения. Не проводить попутный redesign; сохранять layout, размеры, меню, дерево, формы, таблицы, пагинацию и порядок действий, если задача явно не меняет их.
- По смыслу сценария сохранять или реализовывать loading/error/empty/success и предотвращать повторную отправку во время запроса. Ошибка должна быть видима и понятна; disabled-кнопка не должна молча скрывать причину отказа.
- Loader/skeleton показывать только при реальном ожидании, размещать в области заменяемых данных и проверять в light/dark. Не добавлять искусственные задержки и skeleton к сразу готовым формам.
- Обеспечивать клавиатурную навигацию, видимый фокус, подписи input/checkbox и доступное описание ошибок. Проверять tooltip/menu по наведению и фокусу; переход Tab к пунктам не должен преждевременно закрывать меню. Не обозначать ошибку только цветом.
- Для изменяемых password/input проверять обычный ввод, focus, ошибку и browser/password-manager autofill, сохраняя проектный шрифт и цвета в обеих темах.
- На дату адаптации основная оболочка `src/components/mainWindow/mainWindow.tsx` показывает предупреждение при ширине до 600px или высоте до 559px. Не заявлять полноценную мобильную поддержку и не снимать это ограничение попутно. Проверять поддерживаемые размеры, границы ограничения, zoom, длинный текст, открытое/закрытое дерево и отсутствие непредусмотренного переполнения.
- Юридические `/privacy-policy`, `/cookie-policy`, `/user-agreement` имеют отдельный доступный layout для маленьких экранов и обход CAPTCHA-провайдера в `App.tsx`. Сохранять эти свойства и проверять их на desktop/mobile. Не заменять React-страницы PDF-маршрутами из neurobaza.
- Если задача отдельно вводит мобильный UI, обеспечить тот же состав данных, порядок, права и действия; выбор breakpoint/layout описывается в задаче wwwhypda, а не копируется из neurobaza.

### 7. Сохранность кода и пользовательских данных

- Запрет удаления существующих комментариев действует также для закомментированных импортов, вызовов, TSX, SCSS и временно отключённых блоков. Не удалять их как cleanup/unused; отдельное требование пользователя рассматривается отдельно.
- Сохранять `src/components/tree/`, его связи с поиском и состоянием Redux, временно отключённые компоненты/маршруты и код для дальнейшей разработки. Не переносить отсутствующий каталог моделей neurobaza.
- Не очищать и не переименовывать localStorage-ключи, не терять черновики и таблицы измерений из Redux/localStorage вне задачи. При изменении структуры хранения предусмотреть совместимость/миграцию и проверить reload, переходы между шагами ввода и восстановление данных.
- Не менять backend, Docker/Nginx, Redux, API layer, темы и соседние компоненты ради попутного улучшения. Для frontend-only задачи читать backend только в объёме необходимого API/проверки расхождения.

### 8. Проверки и завершение задачи

Для изменения frontend-кода использовать команды wwwhypda из корня приложения `wwwhypda/`. Сборку и lint выполнять в Docker, не копировать сервис `frontend-dev` и `compose.dev.yaml` из neurobaza:

```text
docker compose --env-file .env.development run --rm --build --no-deps frontend npm run build -- --mode development
docker compose --env-file .env.development run --rm --build --no-deps frontend npm run lint
```

Команды используют dev-env без чтения или вывода его содержимого. Если локальное окружение не настроено, указать конкретную недоступную проверку; не обходить запрет чтения env. Проверки адаптировать при явно запланированном изменении Compose.

- Для браузерной проверки использовать dev Nginx по `http://localhost:8080`. Dev stack собирает статический frontend, HMR отсутствует: после правки нужен rebuild штатным способом из README, затем reload. Проверочная одноразовая сборка выше сама не обновляет раздаваемый dev bundle.
- После изменения общих стилей/компонентов проверить все затронутые потребители среди `/`, `/search`, `/documents`, `/about`, `/contribute`, `/login`, `/register`, `/forgot-password`, `/account`, `/superaccount`, `/read`, `/input`, `/edit` и юридических страниц. Список уточнять по актуальному `mainBody.tsx`, а не по маршрутам neurobaza.
- Проверить обе темы, поддерживаемые размеры, нужные роли и состояния. При изменении auth/API транспорта дополнительно проверить login/check/refresh/logout, истёкшую сессию, CSRF-отказ и запрет доступа обычному пользователю к административным действиям.
- При изменении общей формы, skeleton, autofill или tooltip проверить релевантные сценарии в Chrome и Firefox. Если браузерная проверка недоступна, явно сообщить об этом, не выдавая её за выполненную.
- Если полный lint падает на старых проблемах, зафиксировать их отдельно от новых ошибок и выполнить scoped ESLint изменённых TS/TSX-файлов через тот же Docker-сервис. Не выдавать scoped lint за успешный полный lint и не исправлять несвязанные файлы ради зелёного отчёта. SCSS/JSON дополнительно проверять сборкой и релевантными UI-сценариями.
- Документальные изменения без изменения frontend-кода не требуют запуска сборки/lint приложения: проверить целостность текста, согласованность двух ролей и корректность путей.
- После каждой задачи записать в `TASKS.md` результат, изменённые файлы, выполненные проверки, их исход и оставшиеся ограничения. Отметку выполнения ставить после реализации и предусмотренных проверок; недоступные обязательные проверки фиксировать явно.
- Если требуется изменение инварианта или расширение задачи, описать расхождение и передать его архитектору для уточнения `TASKS.md`. Не записывать запланированное поведение как уже реализованное и не вводить дополнительный процесс согласования из neurobaza.
