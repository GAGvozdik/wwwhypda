# Цель

Подготовить часть сайта, связанную с reCAPTCHA, к запуску с соблюдением применимых требований ЕС и Италии: установить допустимый режим по конкретным функциям, выполнить необходимую минимизацию и исправить уведомления. Предпочтительный результат — обоснованный технический security-only режим без необязательного consent-banner, с проверенными договорными условиями и фактической работой. Завершить цикл только после необходимых локальных исправлений и их проверки.

Результат не является обещанием отсутствия штрафов и не должен заранее объявлять всю reCAPTCHA «обязательной». На выходе нужны таблица решений по функциям, подтверждающие сведения и реализованная локальная конфигурация, соответствующая этим решениям. Этот цикл закрывает reCAPTCHA, но не является аудитом всех обработок сайта: почта OVH, deployment и другие незавершённые темы остаются в BACKLOG.

## Объём и ограничения

Локальная оценка, необходимые минимальные изменения CAPTCHA-интеграции, проверка официальных источников, безопасные тесты, браузерная проверка и согласование юридических текстов/внутренних инструкций. VPS, DNS, почта, billing и production-конфигурация не затрагиваются. Не читать env, ключи и секреты; не отправлять реальные письма и научные данные.

В этом цикле разрешены только технические изменения, прямо вытекающие из оценки: уменьшение CAPTCHA-scope, момента загрузки и лишних execute-вызовов; согласование frontend/backend действий; корректная серверная проверка токена. JWT, ownership, CSRF, отзыв сессий, ограничения нагрузки, retention и почту сохранить. Нельзя отключать все меры защиты ради получения вывода «cookies отсутствуют». Новый provider, платная услуга или полноценная consent-система требуют решения пользователя и новой revision; их не внедрять попутно.

Не создавать баннер с принудительным «согласиться со всеми cookies». Не покупать юридические услуги или новые продукты Google, не мигрировать ключи и не включать платные функции автоматически.

## Проверенное исходное состояние

- Используется react-google-recaptcha-v3; App.tsx включает GoogleReCaptchaProvider с useRecaptchaNet на маршрутах из recaptchaRoutes.ts.
- Перечень: /search, /login, /register, /forgot-password, /input, /account, /superaccount, /read, /edit. Информационные и юридические страницы не монтируют provider. При переходе между группами документ перезагружается; это не удаляет уже установленный cookie.
- useAuthCheck выполняет executeRecaptcha('check_auth') для фоновой проверки сессии. В login есть дополнительный check_auth_after_login. Не считать каждый токен отдельной необходимой защитой без проверки цели.
- Есть явные actions регистрации/подтверждения/resend, входа, восстановления, подачи заявки и account actions. Полный список и соответствие серверным endpoint нужно построить по коду; закомментированные вызовы не считать действующими.
- Общий backend verifier — wwwhypda-backend/common_defenitions.py; Flask routes используют verify_recaptcha. Наличие проверки ещё не подтверждает корректность всех hostname/action/score/expiry условий.
- Footer находится в src/components/mainWindow/mainWindow.tsx; строка recaptcha_notice — в src/common/error_messages.json. Badge скрывается стилем в App.css. Уведомление показывается только на группе защищённых маршрутов.
- Пользователь уже находил используемую запись v3 с label wwhypdatestdeployversion в Google Cloud. Не начинать поиск с двух чужих записей и не просить раскрывать secret key.
- Ранее оператор проверил Firefox: на главной запросов reCAPTCHA нет, на поиске/логине появляются, после возврата на главную отсутствуют. Это ограниченная прежняя проверка, не полный аудит cookie/storage и не подтверждение production.
- deploy/privacy/recaptcha-assessment.md содержит предварительную оценку, а не окончательное решение.
- Цикл 002 архивирован; не откатывать реализованные retention-механизмы и новую редакцию договора.

## Правовые вопросы, которые нужно разделить

1. Обработка персональных данных: основание по GDPR, необходимость, баланс интересов, прозрачность, права людей, обработчик и передачи.
2. Доступ/запись на пользовательском устройстве: итальянские правила cookies и иных механизмов. Законный интерес по GDPR сам по себе не заменяет cookie-согласие, если исключение не применимо.
3. Строго необходимая техническая защита: оценка именно запрошенной пользователем функции и объёма, а не только названия cookie или наличия input.
4. Google Customer Data и иные категории сведений: не переносить статус processor на любое поведение Google и не переносить CDPA reCAPTCHA на Gmail.

Стартовые официальные источники, проверенные при планировании 14.10.2026; исполнитель повторно сверяет актуальность и указывает разделы, дату документа и дату доступа:
- [Google FAQ: Data processing и cookie](https://docs.cloud.google.com/recaptcha/docs/faq)
- [Google Cloud Data Processing Addendum](https://cloud.google.com/terms/data-processing-addendum)
- [Google Service Specific Terms, раздел Google Cloud Fraud Defense](https://cloud.google.com/terms/service-terms)
- [Garante: cookie e altri strumenti di tracciamento, 10 июня 2021](https://www.garanteprivacy.it/home/docweb/-/docweb-display/docweb/9677876)
- [GDPR: статьи 5, 6, 13, 21, 22, 25, 28, 35 и глава V](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A32016R0679)

- [Google: actions и серверная проверка reCAPTCHA v3](https://developers.google.com/recaptcha/docs/v3)
- [Google: одноразовые токены и срок действительности](https://developers.google.com/recaptcha/docs/verify)

Google FAQ описывает изменение роли с 02.04.2026 и необходимость пересмотра disclosures. Это довод для оценки конкретного договора, а не отдельное подтверждение решения регулятора по wwwhypda. Правила cookies относятся также к иным технологиям доступа к устройству; пустой cookie-list не доказывает отсутствие обработки.

### 3. [x] Выполнить минимальную локальную browser-проверку

**Результат:** deploy/privacy/recaptcha-browser-check.md с датой, браузером, режимом и таблицей наблюдений. Не хранить cookie-values, токены, email, passwords, содержимое аккаунта или несокращённый HAR.

- Использовать отдельный чистый профиль/приватное окно Firefox или Chrome, без выхода владельца из основного Google-аккаунта. Его личные Google-login cookies не являются результатом аудита сайта.
- Проверить прямую загрузку /, всех юридических страниц и защищённых страниц; переход главная → login/search → главная/юридическая. Для каждой группы проверить Network и storage до взаимодействия и после допустимого тестового действия.

- Не требовать Google production-ключ для localhost, если домены/тестовый режим не подходят: зафиксировать различие и не отключать production verification ради теста. Не читать env и не создавать платные ключи.

**Готовность:** понятен наблюдаемый объём до действий и при действиях, информация/юридические страницы доступны без provider, остаточные ограничения теста названы. Существенные неподтверждённые факты не маскируются словом «проверено».

### 4. [x] Сделать вывод по каждой функции и выбрать минимальный допустимый режим

**Результат:** окончательная таблица решений и обоснование legitimate interests / necessity в assessment.

Для каждого действия, а не общей страницы:
- конкретная угроза и защищаемый пользовательский сервис;
- почему CAPTCHA нужна дополнительно к OVH anti-DDoS, Nginx rate limits, JWT/ownership, CSRF и ограничениям отправки кодов;
- сравнение менее вмешивающихся способов и их фактических ограничений;
- необходимость объёма данных, ранней загрузки и частоты фоновых checks;
- влияние на пользователя, ложные отказы, международные передачи и меры минимизации;
- вывод по GDPR и отдельно по устройству/cookie-исключению;
- решение: оставить без согласия при установленных условиях / ограничить использование / требуется иной режим или дополнительные сведения.

Наличие реальной прошлой атаки не обязательно для профилактической защиты, но нельзя придумывать статистику злоупотреблений. Предупреждения Google о чужих атаках не являются статистикой wwwhypda. Изложить конкретную модель риска и доказательства выбранной меры.

Не считать обязательными все CAPTCHA-токены только потому, что текущий код их требует. Особенно подробно оценить search, protected read, check_auth и check_auth_after_login; чтение/проверка cookie-сессии и изменение данных имеют разные риски. Наличие аккаунта не является согласием на стороннюю обработку.

Предпочтение пользователя — действенная защита без необязательного consent-banner. Это цель выбора минимального допустимого режима, а не юридическое основание. Не строить фиктивную возможность «отказаться» с фактически продолжающимися запросами Google и не снимать все меры защиты при отказе.

Если требуется техническая минимизация, описать точные функции/файлы/endpoint и необходимые сохранённые меры. Зафиксировать выбранную минимальную конфигурацию и выполнить её в шаге 5 этого же цикла. Не переносить обязательную минимизацию до запуска в неопределённый будущий backlog. Если законный вариант без согласия установить нельзя даже после минимизации, запросить решение по конкретной альтернативе; до него не объявлять этап готовым.

**Готовность:** по каждому действию есть аргументированный вывод и условия, а не blanket-утверждение «Google сказал necessary». Если ключевой факт неизвестен, требуется его получение; одна отметка «неизвестно» не закрывает соответствующий критерий.

### 5. [x] Реализовать необходимую минимизацию и корректную проверку

**Файлы по доказанной необходимости:** wwwhypda-frontendV2/src/App.tsx; src/components/commonFeatures/recaptchaRoutes.ts и withRecaptcha.tsx; users/useAuthCheck.tsx, auth/login.tsx и другие реально затронутые handlers; wwwhypda-backend/common_defenitions.py, auth/authentication.py и реальные CAPTCHA-protected endpoints; mainApp.py только для безопасной настройки hostname/action-политики; новый tests/test_recaptcha_policy.py. Не изменять соседние UI-компоненты и unrelated endpoints.

- По результату шага 4 убрать provider/execute для функций, где строго необходимый объём не обоснован; особенно исключить лишние фоновые проверки и повторный check после входа, если JWT/session + существующие меры достаточны. Удаление frontend-вызова и обязательности CAPTCHA на соответствующем backend endpoint должны быть согласованы: нельзя оставить вечный skeleton/401 либо отключить JWT/ownership вместе с CAPTCHA.
- Для оставленных действий выбрать минимальный обоснованный момент загрузки и выполнения. Не делать фоновый сбор сигналов на всех страницах ради качества score, если его необходимость не установлена. Сохранить recaptcha.net и доступность юридических/информационных страниц без Google-запросов. Reload между группами и сохранность drafts проверять при любом изменении этой границы.
- Server-side expected action определяет endpoint, а не JSON пользователя. Проверять соответствие action ожидаемому действию/конкретному конечному списку разрешённых значений для этого endpoint. Проверять hostname по точному allowlist доменов оператора; localhost/test hostname допустимы только в изолированном тестовом/dev-режиме. Hostname не брать из произвольного заголовка клиента и не использовать небезопасный substring-match.
- Сохранять Google server-side verification с success, score и обработкой недействительных/просроченных/повторно использованных токенов. Google siteverify обеспечивает ограничения срока и одноразовости; нельзя считать собственную память worker или отдельное истечение cookie заменой проверки Google. Дополнительную проверку challenge_ts делать только с корректной семантикой и допуском clock skew; не использовать время браузера как доказательство.
- Пустой токен, неправильный action/hostname, неверный score/формат, timeout/ошибка/недействительный token не дают успех на сохраняемой защищённой операции. Test bypass только при настоящий TESTING, не активируется произвольным клиентским значением; RECAPTCHA_ENABLED=False не должен незаметно выключить обещанную защиту при production-конфигурации. Проверить текущие startup guards по исходникам, не читать значения prod-env.
- Подготовить имена необходимых настроек и safe defaults, без чтения/записи секретов. Не выполнять реально платные assessments и не менять Google-проект. Действительные ответы Google и security logs не должны содержать токен или персональные данные.

**Проверки:** unit/HTTP-тесты только с synthetic Flask fixtures, mock verification и без SMTP/рабочей БД. Проверить успех правильного действия, отказ на cross-action/cross-host, invalid/expired/reused token, Google failure, сохранение JWT/CSRF/ownership и отсутствие CAPTCHA-обязательности только на обоснованно освобождённых endpoint. Контракты оставшихся защищённых действий не должны стать обходными.

```text
docker compose --env-file .env.development build backend
docker run --rm --pull=never --network none -e TEST_AUTH_DATABASE_URI=sqlite:// --entrypoint python wwwhypda-dev-backend -m unittest tests.test_recaptcha_policy tests.test_auth_lifecycle tests.test_terms_acceptance tests.test_submission_authors -v
```
