# Проверки и документация

### 8. Проверки и завершение задачи

Для изменения frontend-кода использовать команды wwwhypda из корня приложения `wwwhypda/`. Сборку и lint выполнять в Docker, не копировать сервис `frontend-dev` и `compose.dev.yaml` из neurobaza:

```text
docker compose --env-file .env.development run --rm --build --no-deps frontend npm run build -- --mode development
docker compose --env-file .env.development run --rm --build --no-deps frontend npm run lint
```

Команды используют dev-env без чтения или вывода его содержимого. Если локальное окружение не настроено, указать конкретную недоступную проверку; не обходить запрет чтения env. Проверки адаптировать при явно запланированном изменении Compose.

- Для браузерной проверки использовать dev Nginx по `http://localhost:8080`. Dev stack собирает статический frontend, HMR отсутствует: после правки нужен rebuild штатным способом из README, затем reload. Проверочная одноразовая сборка выше сама не обновляет раздаваемый dev bundle.
- После изменения общих стилей/компонентов проверить все затронутые потребители среди `/`, `/search`, `/documents`, `/about`, `/contribute`, `/login`, `/register`, `/forgot-password`, `/account`, `/superaccount`, `/read`, `/input`, `/edit` и юридических страниц. Список уточнять по актуальному `mainBody.tsx`, а не по маршрутам neurobaza.
- Проверить обе темы, поддерживаемые размеры, нужные роли и состояния. При изменении auth/API транспорта дополнительно проверить login/check/refresh/logout, истёкшую сессию, CSRF-отказ и запрет доступа обычному пользователю к административным действиям.
- При изменении общей формы, skeleton, autofill или tooltip проверить релевантные сценарии в Chrome и Firefox. Если браузерная проверка недоступна, явно сообщить об этом, не выдавая её за выполненную.
- Если полный lint падает на старых проблемах, зафиксировать их отдельно от новых ошибок и выполнить scoped ESLint изменённых TS/TSX-файлов через тот же Docker-сервис. Не выдавать scoped lint за успешный полный lint и не исправлять несвязанные файлы ради зелёного отчёта. SCSS/JSON дополнительно проверять сборкой и релевантными UI-сценариями.
- Документальные изменения без изменения frontend-кода не требуют запуска сборки/lint приложения: проверить целостность текста, согласованность двух ролей и корректность путей.
- После каждой задачи записать в журнале активного stage результат, изменённые файлы, выполненные проверки, их исход и оставшиеся ограничения. Отметку выполнения ставить после реализации и предусмотренных проверок; недоступные обязательные проверки фиксировать явно.
- Если требуется изменение инварианта или расширение задачи, описать расхождение и передать его архитектору для уточнения активного stage. Не записывать запланированное поведение как уже реализованное. Соблюдать двухролевой цикл из docs/WORKFLOW.md.
