# Цель

Реализовать небольшую независимую Python-задачу очистки OVHcloud Zimbra Starter для support@wwhypdatestdeployversion.it. Основа — принятое ТЗ владельца от 16.10.2026 и уточнения безопасности ниже. По умолчанию только DRY_RUN. Никаких реальных удалений и deployment без отдельно согласованной приёмки на реальном ящике. По уточнению владельца заключительный шаг включает локальное согласование Privacy Policy, User Agreement и Cookie Policy с проверенной схемой почты; инструкция обычного локального запуска сохраняет Gmail как поддерживаемый вариант. Все три документа скачиваются как PDF; при изменении редакции пользователь явно принимает актуальную версию User Agreement и подтверждает ознакомление с политиками до получения обычного доступа к аккаунту.

## Границы и зависимости

- Работать локально в wwwhypda. Не читать env/секреты/current_todo_list.md, не выполнять VPS/DNS/реальные письма, commit/push. Сохранить незакоммиченные изменения SMTP цикла 007 и остальные чужие изменения.
- SMTP уже подготовлен локально (архив 007); реальная backend-доставка ещё не проверена. Webmail/SPF/DKIM/DMARC/ящик/DPA подтверждены владельцем. Стандартный SMTP-код не делает IMAP APPEND и не обязан оставлять Sent-копии; фактическое поведение сервиса не установлено.
- IMAP imap.mail.ovh.net:993 SSL/TLS, пароль именно ящика. Использовать стандартные imaplib/email/ssl/sqlite3/calendar/zoneinfo; не вводить новый сервер, UI, тикетную систему, Google Apps Script, PostgreSQL-миграции или новый framework.
- Не менять восстановление пароля, JWT/CSRF/reCAPTCHA или текущие сроки аккаунтов/заявок ради почтовой очистки. Дополнительное прямое поручение владельца разрешает строго необходимые изменения login/session gates и хранения доказательств принятия для шага 10. Регистрационное принятие согласовать с общим механизмом, не переписывая остальной auth-flow. По новому поручению разрешены локальные правки трёх публичных политик и текущего контакта в шаге 8, только по проверенным фактам, с синхронной версией договора. Это заменяет прежний запрет на их изменение в этом цикле. Не отключать очистку старого Gmail до отдельного решения по старой переписке. В README/инструкции для обычного локального запуска сохранять Gmail; настройки production OVH описывать отдельно в deploy/mail, не выполнять массовую замену Gmail в репозитории.
- Минимальный набор файлов: wwwhypda-backend/maintenance/mail_cleanup.py и небольшие helpers рядом при необходимости; tests/test_mail_cleanup.py; deploy/mail/ovh-cleanup.md; изолированные fixtures/test entrypoint, .gitignore и deploy/mail/systemd/*.service/*.timer при необходимости. Не импортировать mainApp/Flask auth/DB/env loader. Использовать уже существующий backend-образ для one-shot CLI, не постоянно работающий новый микросервис.
- Сроки: одно календарное месячное приращение от исходной даты, а не 30 суток. Хранить aware UTC, сравнивать с add_calendar_month(timestamp) < now; последний день короткого месяца корректно ограничивать календарём. Отсутствующие/невалидные/future даты не выдумывать, часы не подставлять из ненадёжного Date-header. Расписание отдельно Europe/Rome.

## Обязательные корректировки исходного ТЗ

1. Фактические Sent/Drafts определять по SPECIAL-USE и подтверждённой точной карте папок, не только по английскому имени. WWHYPDA-Closed — ручная отметка владельца, не автоназначение по возрасту.
2. Закрытым для автоматического удаления считать только однозначную цепочку, все доступные копии сообщений которой находятся в Closed; исходящие ответы снаружи также требуют ручного помещения в Closed. Утилита не удаляет поддержку из Inbox/Sent/Trash/других папок ради очистки закрытой цепочки.
3. После нового ответа/удаления из Closed состояние становится reopened и не получает новое closedAt только потому, что старые письма остались в Closed. Нужен наблюдаемый новый ручной цикл закрытия; при ненаблюдаемой операции или неоднозначности — запрет удаления и понятная операторская процедура повторного закрытия без ручного редактирования SQLite.
4. DRY_RUN не выполняет STORE/MOVE/COPY/APPEND/EXPUNGE/CREATE и не меняет Seen: EXAMINE/readonly selection и BODY.PEEK. Запрещён обычный EXPUNGE, включая неявный через CLOSE в cleanup/finally/context manager. Закрывать соединение безопасным UNSELECT при поддержке либо LOGOUT/shutdown без CLOSE.
5. UIDPLUS защищает выбор конкретных UID, но не делает транзакцией проверку всей переписки и последующее удаление. Между сканированием и командой может прийти новый ответ. Не обещать невозможную абсолютную атомарность IMAP между папками: перед execute доказать применимость ограничений, повторную проверку и поведение при изменениях; неоднозначная поддержка остаётся без автоудаления. Отдельный флаг включения support-delete по умолчанию False, даже если service-delete позже включён.
6. Локальные тесты не доказывают capabilities/поведение конкретного Zimbra. Цикл не архивировать до получения предусмотренного ниже реального подтверждения безопасного адресного удаления; отсутствие писем в Sent не повод искусственно создавать их копии.

## Шаги

### 1. [x] Изучить протокол и сделать безопасный preflight

- Прочитать deploy/mail/ovh-smtp.md, относящиеся условия из родительской mail docks и текущие шаблоны отправки. Сверить Flask authentication.py и password_reset_delivery.py, но не менять их.
- По первичным источникам ниже уточнить UIDPLUS, UIDVALIDITY, UIDNOTSTICKY, SPECIAL-USE/папки, readonly/PEEK, неявный EXPUNGE при CLOSE. Стандарт не подтверждает фактическую поддержку OVH: preflight только считывает CAPABILITY после логина, LIST/attributes/delimiter и доступность нужных папок.
- IMAP4_SSL с ssl.create_default_context(), проверкой сертификата и hostname, socket timeout, без debug/raw server response в логах. Ошибки сертификата/логина/доступа прекращают проход без небезопасного fallback. Пароль никогда не является аргументом CLI, частью команды, URL или журнала.
- Операторская карта папок не выводится в обычный агрегированный журнал: названия пользовательских папок тоже могут раскрывать данные. Безопасная опциональная локальная процедура настройки даёт владельцу выбрать точные Sent/Closed/Drafts; агент не читает содержимое ящика или секреты напрямую. Не создавать папки автоматически: инструкцию WWHYPDA-Closed выполнить владельцу через Webmail.
- Если нет однозначного Sent, служебное удаление отключено. Если нет однозначного Drafts/Closed или невозможно прочитать одну из нужных папок, support-delete отключено. UIDNOTSTICKY/нет UIDPLUS/нет права адресного удаления — execute запрещён, только отчёт.
- Приёмка: preflight понятен, безопасен и протестирован на fake IMAP; реальные capabilities пока записаны как неизвестные.

### 2. [x] Реализовать полный ограниченный снимок и точное распознавание служебных писем

- Сканировать все доступные папки для проверки ссылок/новых ответов/черновиков: Inbox, Sent, Closed, Drafts, Spam/Trash и пользовательские папки, без молчаливого пропуска. NoSelect контейнеры корректно отличать от непрочитанной папки. Неполный снимок/time limit/ошибка чтения запрещают execute по зависящим от полноты правилам.
- UID FETCH/SEARCH, не sequence numbers; пачки (например 100 UID), конечный верхний предел по UIDNEXT начального снимка и ограниченные UID-диапазоны, а не гигантский UID SEARCH ALL. Размер заголовка/тела и общее число сообщений ограничивать; превышение — skip/fail closed, не молчаливое обрезание с объявлением снимка полным. Перед execute проверить новые UID/изменения.
- Получать заголовки и INTERNALDATE через PEEK, тело только у кандидатов. Message-ID/References/In-Reply-To разбирать строго; тема и From сами по себе не доказывают принадлежность цепочке или реальную отправку приложением.
- Служебные кандидаты только в подтверждённом Sent, один точный From support@wwhypdatestdeployversion.it; Subject и полное декодированное text/plain тело после strip соответствуют одной паре:

| Subject | Полное тело, [0-9]{6} — ровно шесть ASCII-цифр |
| --- | --- |
| Activate your account | Your activation code: [0-9]{6} |
| Your new activation code | Your new activation code: [0-9]{6} |
| Password Reset Code | Your password reset code: [0-9]{6} |

- Только fullmatch, не substring/Unicode \d. MIME defects, неизвестный charset, HTML/attachment/несколько альтернативных частей, дубли From/Subject, In-Reply-To/References или любая обнаруженная связь с обращением/ответом/черновиком — skip. Не извлекать лишь подходящую строку из более длинного письма и не удалять поддержку с похожей темой.
- Возраст по корректному aware INTERNALDATE (как минимум месяц хранения этой копии), не клиентскому Date. Перемещение с сохранением/сменой даты не делает письмо старше достоверного возраста. Если у текущего SMTP нет Sent-копий — matched=0, ничего не добавлять в Sent для будущего удаления; самостоятельно не посылать тестовые коды.
- Приёмка: точное распознавание и исключение всех неясных случаев, даты/месяцы/нулевая выдача/полнота протестированы.

### 3. [x] Реализовать состояние закрытия и повторного открытия обращений

- SQLite вне Git/образа, постоянный host bind directory для контейнерного запуска, каталог 0700/файл 0600 и тот же постоянный namespace для lock. Описать путь, права, сохранность при recreate и защиту от запуска второго экземпляра. Не менять PostgreSQL.
- Хранить только необходимые closedAt, статус, mailbox identity+UIDVALIDITY+UID, отпечатки состава/контента/ссылок и журнал опасных операций. Не сохранять адреса/темы/тела/коды/пароли. Для сравнения Message-ID, participants и данных использовать HMAC со стабильным локальным ключом 0600, отдельно от логов/репозитория; это псевдонимизированное состояние, не обещание полной анонимности. Потеря ключа/SQLite/битый state => новый безопасный baseline, а не немедленная очистка старых Closed.
- Граф переписки по Message-ID/In-Reply-To/References во всех папках. Дубли/противоречивые IDs, неполные ссылки, цикл, недостающие поля, неясные копии — skip; идентификатор не является ключом IMAP-удаления. Сходство subject/участников можно использовать лишь как дополнительный запрет при подозрении на ответ без References, а не положительное основание объединения/удаления. Не обещать распознать любой человеческий ответ без технических связей.
- closedAt — момент первого полного успешного наблюдения однозначной, полностью находящейся в Closed цепочки. Не брать возраст исходного письма. Открытая цепочка/часть снаружи Closed не закрывается по бездействию. Месяц отсчитывается от первого наблюдения, даже если письмо старое.
- Новое входящее/исходящее связанное сообщение, черновик, изменение состава/содержимого, перенос наружу или смена UIDVALIDITY отменяют разрешение удаления и старую дату. Reopened — устойчивое состояние, не новый recently_closed при следующем запуске. Описать безопасный повторный ручной цикл: наблюдаемое возвращение всей цепочки наружу Closed, затем новое перемещение целиком в Closed. Если операции между проходами не наблюдались, автоматическое закрытие не считать доказанным; предусмотреть узкую явную операторскую отметку повторного закрытия/инструкцию, без редактирования DB вручную и без веб-тикетной системы.
- Черновик, который невозможно уверенно отнести/исключить (в том числе без Message-ID/References), блокирует подозреваемое обращение; если круг связей установить нельзя — support-delete текущего прохода. Любое сомнение оставляет письма.
- DRY_RUN может обновлять только локальное состояние первого наблюдения; явно отметить, что эти даты продолжаются при переключении execute, но разрешение удаления всё равно требует свежей полной проверки. Смена ящика/host/карты папок инвалидирует разрешения, нельзя переиспользовать state другого ящика.
- Атомарные SQLite transactions и lock; ограниченный срок хранения завершённых операционных записей описать и проверить. Не копить бессрочно удалённую переписку/сырые Message-ID для журнала. Потеря state/откат backup не должен сокращать срок или расширять удаление.
- Приёмка: state transitions open/recently_closed/reopened/expired/unsafe детерминированы и проверены; неизвестные даты/UIDVALIDITY не ведут к удалению.

### 4. [ ] Реализовать адресное окончательное удаление и восстановление после сбоя

- По умолчанию dry-run. Execute требует явного MAIL_CLEANUP_DRY_RUN=false и CLI --execute одновременно; для поддержки дополнительно MAIL_CLEANUP_SUPPORT_DELETE_ENABLED=true после отдельной приёмки. Ошибочное значение флага — отказ, не False по умолчанию. --dry-run всегда сильнее execute.
- Перед первой мутацией: полный свежий снимок, capabilities UIDPLUS, допустимый UIDVALIDITY, ровно те же fingerprint/состав/closedAt и возраст, отсутствие Draft/новых ответов/помеченных чужим клиентом Deleted; неизменившаяся карта и разрешения папок. Повторить непосредственно перед каждой порцией. Ни один UID не берётся из другого mailbox/UIDVALIDITY или sequence index.
- Удалять только точный замкнутый UID set целевых сообщений: UID STORE +FLAGS.SILENT (\Deleted), затем UID EXPUNGE с этим же набором. UID range допускается лишь без промежуточных нецелевых UID; не использовать wildcard *. Не вызывать обычный EXPUNGE, CLOSE, очистку Trash или временное снятие чужих Deleted как fallback. Отсутствие UIDPLUS/ошибка проверки => ноль новых STORE/удалений.
- До STORE атомарно записать intent и проверенные identities; после каждой команды записывать outcome. Разрыв после STORE/EXPUNGE может оставлять неизвестный исход: при новом проходе только reconcile по тем же identity/UIDVALIDITY/fingerprint, не удалять заново по старым UID, не отмечать весь batch успешным. Проверить, какие UID действительно исчезли. Не снимать/ставить флаги на посторонних сообщениях при восстановлении.
- При обнаруженном ответе/ошибке после первой порции остановить оставшееся удаление и зафиксировать частичный исход агрегированно; не обещать rollback уже окончательно удалённых сообщений. Не продолжать всю цепочку вслепую ради завершения batch. Не оставлять в finally вызовы, способные expunge чужие Deleted.
- Специальная приёмка гонок: стандартный IMAP не даёт атомарной транзакции «проверить все папки и удалить цепочку». Проверки UIDNEXT/MODSEQ/повторный scan — обнаружение части изменений, а не доказательство отсутствия будущего прихода. CONDSTORE/QRESYNC при наличии не объявлять решением атомарности между папками. Если принятые требования безопасного support-delete нельзя обеспечить, флаг поддержки остаётся запрещён и этот обязательный шаг не считается выполненным: вернуть конкретное ограничение архитектору/владельцу, не ослабляя требования молча.
- Приёмка: fake IMAP доказывает точный UID set и отсутствие побочных expunge при любой ветке/ошибке; реальный UIDPLUS и поведение Zimbra подтверждаются отдельно в шаге 7.

### 5. [x] Подготовить настройки и ежедневный запуск без deployment

- CLI --once/--dry-run/--execute/безопасный preflight; не встраивать очистку в HTTP startup или auth worker. Предпочесть systemd oneshot+timer для существующего образа и отдельного постоянного state bind. Можно добавить отдельный deploy/mail/cleanup.compose.yml, без подключения задачи к обычному up/deployment и без PostgreSQL-сервиса.
- Предложенные env имена: MAIL_CLEANUP_IMAP_HOST (imap.mail.ovh.net), MAIL_CLEANUP_IMAP_PORT (993), MAIL_CLEANUP_IMAP_USERNAME (адрес support), MAIL_CLEANUP_IMAP_PASSWORD (владелец вводит сам; допускается явно документированное использование уже инжектируемого MAIL_PASSWORD без копирования секрета), MAIL_CLEANUP_DRY_RUN=true, MAIL_CLEANUP_SUPPORT_DELETE_ENABLED=false, MAIL_CLEANUP_SENT_FOLDER, MAIL_CLEANUP_CLOSED_FOLDER=WWHYPDA-Closed, MAIL_CLEANUP_DRAFTS_FOLDER, MAIL_CLEANUP_STATE_DIR, MAIL_CLEANUP_BATCH_SIZE=100, MAIL_CLEANUP_MAX_RUN_SECONDS=900, MAIL_CLEANUP_IMAP_TIMEOUT_SECONDS=15. Никакой пароль/Message-ID в argv или журнале.
- Europe/Rome: OnCalendar=*-*-* 01:30:00 Europe/Rome, AccuracySec=1min, без RandomizedDelaySec вне окна и без Persistent catch-up среди дня; проверить systemd calendar/DST в инструкции. Runtime cutoff 01:00–02:00 Rome для планового execute; ручной dry-run возможен вне окна, execute вне окна только отдельным явным операторским решением и описанной командой. Смена DST не даёт второго удаления благодаря lock/state.
- Межпроцессный nonblocking lock на persistent host path + общий лимит времени, deadline действует на сеть и обход; SIGTERM/timeout оставляют корректный journal. Окончание бюджета не даёт использовать частичный scan для удаления. Не помещать state в /tmp/контейнерный writable layer и не разрешать независимые lock-файлы у двух экземпляров.
- Системные unit/Compose — только шаблоны в repo; не запускать systemctl/install/cron на VPS в этом цикле. Owner-инструкция: создание Closed в Webmail, сохранение state/прав, инжекция env runtime без печати, preflight, dry-run, диагностика, отключение таймера без потери state и порядок будущего разрешения execute.
- Приёмка: задания не активируются сами, локальные state/пример env игнорируются Git, расписание/границы/права/неразглашение описаны.
