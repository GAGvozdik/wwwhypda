# Порядок работы двух чатов

## Источник состояния

STATE.md указывает единственный активный файл в docs/stages и последний архивный цикл. Если active_stage: null, имплементатор не выбирает задачи из BACKLOG или старого TASKS сам: нужен новый план архитектора. README файлов и шаблон не являются планами.

В новом чате и после потери контекста прочитать docs/README.md, свою роль, docs/WORKFLOW.md, docs/STATE.md, активный план и указанные в нём правила. Пересказ чата не заменяет файлы.

## Цикл

1. Архитектор изучает цель, актуальный код и правила. Создаёт docs/stages/NNN-short-name.md по шаблону и указывает путь в STATE.md. Пользовательское «составь план» уже разрешает записать план; не требовать отдельного разрешения на сохранение.
2. План содержит конкретные шаги, файлы, ограничения, проверку и условия завершения. Его начальный статус — ready. Создание плана не разрешает реализацию; пользователь передаёт план имплементатору.
3. По поручению выполнить план имплементатор ставит in_progress и последовательно выполняет шаги. Не спрашивает подтверждение каждого обратимого шага в согласованном объёме.
4. После проверки шага ставит [x] и записывает результат, файлы, проверки и ограничения в журнал этого же плана. Одновременно обновляет относящиеся к изменению README и фактические правила.
5. Если требуется изменение объёма или инвариантов, записывает расхождение и возвращает план архитектору. Архитектор уточняет тот же файл, увеличивает revision; завершённые шаги не теряются. Второй активный план не создаётся.
6. Когда все шаги и критерии выполнены, имплементатор ставит completed, затем переносит тот же файл в docs/archive и ставит archived. Это обязательная часть поручения, отдельное разрешение на архивирование не нужно. В STATE.md: active_stage: null, last_archived: путь архива. Записать дату и итог; будущие вопросы добавить в BACKLOG, не объявлять их выполненными.
7. Пользователь возвращается к архитектору и задаёт цель следующего цикла. Архитектор выбирает следующий номер по stages и archive; номера не повторяются.

Статусы: ready → in_progress → completed → archived. STATE.md содержит только ссылки, без копии статуса и задач; статус хранится в плане.

## Не завершено

Невыполненная обязательная проверка или зависимость не позволяет отметить шаг завершённым и архивировать цикл. Записать причину и доступные результаты. Старые несвязанные lint-ошибки можно отделить от новых, если план разрешает такой критерий. Пользователь может исключить работу из объёма; архитектор фиксирует это и переносит её в BACKLOG до завершения.

## Автодокументация

- План: задачи, результаты каждого шага, проверки, финальный итог и ограничения.
- rules: устойчивые требования и проверенное текущее поведение, без истории чатов.
- README приложения: актуальные команды и настройка, если изменились.
- deploy/privacy: действующие подробные внутренние privacy-инструкции; не создавать противоречащие копии.
- BACKLOG: будущие темы, без автоматического разрешения на реализацию.

Планируемое поведение явно обозначать как планируемое. Обновлять фактическое описание вместе с реализацией и проверкой, не заранее. Архитектор может обновлять нормативные правила в рамках задания; имплементатор меняет их смысл только по плану. Механическая синхронизация путей и проверенных фактов допустима в рамках шага. Указать затронутые правила в журнале.

## Коммиты

Планирование: docs(stage-002): plan ovh email migration
Реализация: fix(stage-002): configure ovh smtp
Завершение: docs(stage-002): archive completed plan

Формат: type(stage-NNN): конкретное изменение. Типы feat, fix, refactor, test, docs, chore. Номер одинаковый для всего цикла. Один проверенный шаг может быть отдельным коммитом; мелкий цикл допустимо завершить одним коммитом с кодом и архивом. Агент предлагает название, но не делает commit/push без поручения. Не добавлять чужие изменения через git add .

Исторический снимок TASKS в archive/legacy не является завершённым stage и не участвует в нумерации.
