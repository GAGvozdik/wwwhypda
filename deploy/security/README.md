# Ограничения API в nginx

Обновлены nginx.dev.conf и отдельный production nginx.conf. Production-файл игнорируется Git: его передают на VPS через SFTP. Новые библиотеки и модули не устанавливаются; используются штатные модули существующего nginx:stable-alpine.

## Начальные значения

| Область | Средняя частота | Допустимая короткая серия сверх текущего темпа |
| --- | --- | --- |
| API с одного IP | 10 запросов/сек | 30 |
| API суммарно | 50 запросов/сек | 100 |
| Защищённые POST авторизации с одного IP | 30 запросов/мин | 10 |
| Защищённые POST авторизации суммарно | 5 запросов/сек | 20 |

Все ограничения применяются одновременно. Это ограничители среднего темпа с burst, а не счётчики фиксированного календарного окна. nodelay разрешает короткую серию сразу, но отклоняет дальнейший избыток. Лимит авторизации общий для входа, регистрации, подтверждения, повторной отправки кода, запроса и подтверждения восстановления пароля. Чтение сессии, logout и refresh его не расходуют; на них остаётся общий лимит API.

Дополнительно /api/ допускает до 20 одновременно обрабатываемых запросов с IP и до 100 суммарно. Эти счётчики начинают учитывать запрос после чтения заголовков; это не лимит всех открытых TCP-соединений. Заголовки ожидаются до 10 секунд, новые порции тела — до 30 секунд. Подключение к backend ограничено 5 секундами; интервалы отправки и чтения proxy — 30 и 60 секундами.

Избыток отклоняется до proxy к backend с кодом 429 и безопасным JSON-сообщением. Сайт и статические файлы не расходуют лимит API. Клиент определяется по сетевому адресу, а не присланному X-Forwarded-For. Если перед VPS появится доверенный reverse proxy/CDN, настройку реального IP нужно согласовать с его адресами, не доверяя произвольным заголовкам.

## Эксплуатация

Это начальная настройка без измерения ёмкости VPS. Общие ограничения ограничивают нагрузку с разных IP, но при атаке могут также отклонять законные запросы. Пользователи университетской сети могут разделять один внешний IP. По штатной нагрузке и частоте 429 пересматривать значения; не отключать защиту целиком для устранения ложных блокировок. Число 50 запросов/сек не доказывает способность приложения безопасно обработать такой темп: отдельный запрос может быть дорогим.

nginx, backend-лимиты, reCAPTCHA и сетевая Anti-DDoS-защита OVH дополняют друг друга. Эти настройки не гарантируют доступность при любом DDoS и не заменяют внешнюю фильтрацию сетевого потока.

## Проверка и применение

Изолированная проверка с временным nginx и тестовым backend: python deploy/security/check_nginx_limits.py. Требуются Docker и существующие локальные образы nginx:stable-alpine и wwwhypda-dev-backend; загрузки образов и установки зависимостей нет. Тест проверяет обычные запросы, общий счётчик auth-маршрутов, код 429, отсутствие пересылки отклонённых запросов, нормализованные пути и отсутствие обхода через X-Forwarded-For. Production-структура проверяется с удалёнными только в тестовой копии TLS-директивами; реальные сертификаты проверяются на VPS. Распределённая нагрузка и пределы соединений отдельно не нагрузочно измерены.

После передачи nginx.conf на VPS: sudo docker compose -f docker-compose.prod.yml run --rm --no-deps nginx nginx -t. Если проверка успешна и nginx уже работает: sudo docker compose -f docker-compose.prod.yml exec nginx nginx -s reload. Остановленный сайт этой проверкой и загрузкой конфигурации не запускается.

Состояние лимитов находится в памяти nginx, отдельные cookies не создаются. Изменение целей обработки персональных данных не вводится: это существующая цель безопасности. Срок хранения журналов регулируется ранее установленной отдельной настройкой логирования.
